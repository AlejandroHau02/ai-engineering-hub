# ADR-0007 — SYNCODE Desktop: Tauri 2 con Python embebido y puente cerrado

**Estado:** Propuesto (SYNCODE Desktop, Fase 1 — prototipo Doctor).

## Problema

La interfaz local de gestión ([issue #4](https://github.com/AlejandroHau02/ai-engineering-hub/issues/4)) necesita una app de escritorio para Windows que no reimplemente la lógica de SYNCODE, no dependa del Python que tenga instalado el usuario ni amplíe la superficie de ejecución más allá de los contratos de [SYNCODE_CLI_CONTRACT.md](SYNCODE_CLI_CONTRACT.md).

## Decisión

1. **Shell:** Tauri 2 con WebView2. Frontend estático en HTML/CSS/JS sin frameworks ni npm.
2. **Núcleo:** los scripts Python existentes, sin cambios, ejecutados por el **paquete embebible oficial de CPython** (3.12.10, SHA-256 fijado) que se distribuye dentro de la app. El `python312._pth` se reescribe a rutas relativas fijas sin `import site` y el intérprete se invoca con `-I -B`.
3. **Recursos:** solo se empaqueta una lista explícita (Doctor y su grafo de imports, `core/`, `adapters/`, `skills/*/SKILL.md`, `specialists/catalog.json`, `registry/approved-skills.json` y las baselines v0.1) con el layout del repositorio, para que `ROOT = Path(__file__).resolve().parents[1]` funcione igual. `BUNDLE_MANIFEST.json` registra el commit de origen y los hashes.
4. **Puente:** comandos Tauri **tipados y fijos**, uno por operación del contrato, sin parámetros libres. En Fase 1 existe solo `run_doctor`. La capability del webview concede exclusivamente los permisos generados para esos comandos (sin `core:default` ni plugins). No hay ejecución genérica (`run_script(args)`), shell, ni acceso a fs/red desde el webview.
5. **Proceso hijo:** `std::process::Command` sin shell, `env_clear()` más allow-list, `CREATE_NO_WINDOW`, stdin nulo, stdout limitado (1 MiB) y stderr drenado en hilos para evitar bloqueos, timeout con terminación y una sola ejecución simultánea.
6. **Rust valida el contrato; la UI solo presenta.** La clasificación distingue resultado (`report`), error de Doctor (`doctorError`) y fallo de transporte (`transport`). Los invariantes (exit ↔ payload, `schemaVersion` entero 1, `product`, un único objeto ASCII) son estrictos; los campos, estados y `errorCode` nuevos se toleran por ser aditivos y la UI los muestra como «desconocido», nunca como «al día».

## Alternativas consideradas

- **Electron:** mayor tamaño y superficie (Node en el proceso principal) sin ventaja para una pantalla de diagnóstico.
- **Reescribir Doctor en Rust:** duplicaría lógica de dominio y rompería la fuente única de verdad.
- **Usar el Python del sistema:** no reproducible y vulnerable a `PYTHONPATH`, site-packages y versiones distintas.
- **PyInstaller/Nuitka:** añaden dependencias de terceros y empaquetado opaco; el paquete embebible oficial basta.
- **Servidor HTTP local:** contradice los límites del contrato (sin servicios ni procesos de fondo).

## Consecuencias

- Las actualizaciones del núcleo requieren recompilar la app (fuera de alcance en Fase 1).
- El paquete crece unos 20 MB por el runtime.
- `python.exe` embebido no está firmado por SYNCODE; la firma de código y SmartScreen quedan pendientes.
- **Fase 2 (Plan/Apply):** reutilizará el mismo ejecutor interno, pero con comandos tipados nuevos (`plan`, `apply` con la huella guardada en Rust, nunca recibida libremente desde JS), timeout y política de terminación propios (matar Apply deja estado desconocido y obliga a ejecutar Doctor), y el mismo constructor de entorno que Doctor para que el home normalizado de la huella coincida.
