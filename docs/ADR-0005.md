# ADR-0005 — Primera promoción controlada de skills aprobadas

**Estado:** Propuesto para PR #10 (v0.3).

## Problema

El registro de aprobaciones del PR #9 es solo una declaración humana validada estructuralmente. No garantiza que el contenido remoto coincida con la revisión aprobada ni que una instalación conserve los archivos del usuario.

## Decisión

- Optar por un primer incremento **estrictamente limitado a skills autónomas de un único `SKILL.md`**. Las skills con scripts, referencias, assets u otros archivos bajo su directorio se bloquean. No se presentan como instaladas parcialmente.
- `scripts/approved_installer.py` se ocupa solo de verificar y preparar contenido. `scripts/sync.py` conserva la única vía de escritura.
- `sync.py --approved-skills` es una opción **explícita** e independiente de `--specialists` y `--upgrade-skills`. Sigue haciendo **dry-run por defecto**, sin realizar cambios en el home.
- La operación lee exclusivamente `registry/approved-skills.json` del propio checkout. El registro comienza vacío; no se aprueba ni se instala ninguna skill externa en este PR.
- Validar **todo el manifiesto** antes de leer fuentes remotas. Cada target solicitado debe tener estado `tested`; `unsupported` o `not-verified` bloquea la operación antes de cualquier escritura. Para skills incompatibles con uno de los clientes, el usuario debe seleccionar solamente el target compatible.
- Consultar exclusivamente la API pública de GitHub. El contenido se vincula al **SHA de commit de 40 caracteres** y se verifica contra el árbol de Git (ruta, tipo regular, mode y SHA del blob); validar SHA Git del contenido y SHA-256 aprobados, el límite de tamaño, UTF-8, saltos LF, nombre y descripción de una sola línea no ambiguos en el frontmatter.
- Reutilizar `ensure_safe`, `Change`, `verify_change` y `write_with_backup` del instalador existente, con preflight de todos los destinos antes de escribir. Un directorio de skill preexistente se bloquea si falta `SKILL.md` o contiene otros archivos; solo el directorio con un único `SKILL.md` idéntico se trata como no-op idempotente. Un archivo existente con bytes diferentes bloquea **toda** la operación.
- Mantener sin modificaciones los perfiles globales no gestionados y las skills de otros proveedores. Ningún contenido remoto se ejecuta; no se clonan repositorios, descomprimen archivos ni instalan paquetes.

## Restricciones y amenazas

- Un hash correcto **no demuestra seguridad**. La aprobación en Git es una declaración que depende de la revisión del propietario, no una firma criptográfica ni prueba de licencia. Antes de incorporar skills, la revisión humana debe comprobar licencia, dependencias y permisos necesarios.
- El instalador no soporta por ahora bundles, symlinks, submódulos, archivos binarios ni nombres de skills reservados por Windows. Los respaldos exclusivos requieren compatibilidad del filesystem con enlaces duros en el mismo volumen; si no está disponible, la operación se rechaza y se revierte. Si el árbol está truncado o tiene archivos vecinos, rechazar.
- Se rechazan archivos con CR porque el escritor gestionado normaliza saltos a LF y debe conservar los bytes aprobados. Se rechaza NUL; el Markdown debe tener frontmatter con el mismo ID aprobado.
- Se añade `scripts/transaction.py`: antes de escribir prepara un **registro persistente**, hashes nuevos y copias exactas de todos los originales bajo `~/.ai-engineering-hub-transaction/`; ejecuta el lote y, ante una excepción ordinaria, intenta revertir sus archivos y los directorios recién creados. Los respaldos `*.bak.*` se publican después de verificar todo el lote, de forma exclusiva y sin archivos incompletos. Si hubo una interrupción abrupta, una ejecución posterior de `sync.py --recover` valida el registro y restaura únicamente archivos que siguen coincidiendo con el estado original o el instalado por la transacción. No pisa modificaciones ajenas.
- Un bloqueo exclusivo de sistema operativo bajo `~/.ai-engineering-hub.sync.lock` serializa aplicaciones y recuperaciones, rechazando `--recover` mientras haya una instalación activa. El archivo de bloqueo es persistente (no se elimina) y se libera al cerrar el proceso; se detectan archivos preexistentes con contenido inesperado.
- La transacción se aplica también a las skills propias y los especialistas cuando se usa `--apply`. El modo normal continúa sin red y el dry-run sigue sin escritura. Se bloquean symlinks y *junctions*/reparse points en Windows (con fallback para Python 3.10/3.11), con revalidación antes de sustituciones.
- **Limitaciones:** no existe una única operación atómica que haga visibles todos los cambios a la vez; el rollback ante interrupciones requiere `--recover` explícito; la durabilidad de metadatos de directorios tras apagones depende del sistema operativo y filesystem. No se eliminan totalmente las carreras TOCTOU. Un journal, snapshot o archivo intervenido por otro proceso exige revisión manual; un corte antes de crear el journal puede dejar una carpeta temporal sin estado verificable. Se limita la recuperación a 300 archivos y snapshots de 16 MiB por original.
- Las consultas de red ocurren solo si se solicita `--approved-skills` y el manifiesto tiene registros aprobados; el flujo normal de `sync.py` permanece offline. La compatibilidad de todo el manifiesto se valida antes de consultar cualquier origen, evitando descargar un candidato si otro destino solicitado es incompatible.
- La interfaz de CLI **no incorpora ningún comando autónomo de ejecución de skills**. Instalar archivos declarativos no equivale a invocar agentes de manera automática.

## Próxima etapa

Para instalar skills con directorios completos se necesita un manifiesto de **todos** sus archivos (rutas relativas seguras, tamaño, modo y SHA-256, exclusión de enlaces simbólicos y paths escapados), lectura pinneada y verificada y un plan de instalación múltiple con rollback probado. No habilitar esto sin nuevo ADR y pruebas.
