# ADR-0009 — SYNCODE Desktop Fase 2B: aplicación vinculada e integridad en ejecución

**Estado:** Propuesto (SYNCODE Desktop, Fase 2B). Amplía [ADR-0006](ADR-0006.md), [ADR-0007](ADR-0007.md) y [ADR-0008](ADR-0008.md).

## Problema

Hay que poder aplicar desde la interfaz una sincronización ya revisada, con el núcleo Python y sus garantías transaccionales, sin que una vista previa obsoleta autorice cambios distintos. Antes de cualquier escritura, el código que se va a ejecutar tiene que ser el que se publicó.

## Decisión

### 1. Integridad (ancla compilada en el ejecutable)
- `build.rs` calcula el SHA-256 de **cada archivo** de `resources/python` y `resources/syncode` (incluido `BUNDLE_MANIFEST.json` y el `._pth` reescrito) y lo incrusta como tabla en el exe. Si los recursos no están preparados, la tabla queda vacía y nada se ejecuta.
- Antes de **cada** proceso (Doctor, vista previa, aplicación), `integrity::pin`:
  - exige el conjunto exacto de archivos, sin que falte ni sobre ninguno. Un `python/transaction.py` o un `__pycache__/*.pyc` plantados se rechazan, porque `._pth` pone `.` antes de `..\syncode\scripts`;
  - rechaza reparse points (junctions, symlinks);
  - rechaza `pyvenv.cfg` y `*._pth`/`*.pth` junto a la carpeta del paquete, porque CPython los lee en el directorio padre del intérprete;
  - abre cada archivo permitiendo solo lecturas compartidas (`FILE_SHARE_READ`), lo hashea por ese mismo handle y vuelve a enumerar al final.
- Los handles se mantienen hasta que el proceso hijo termina: mientras tanto, el sistema rechaza escrituras y borrados de los archivos verificados.
- Un fallo da `IntegrityFailed`, antes de lanzar nada.
- El directorio de trabajo del hijo es `python/`. `PATH`/`PATHEXT` solo llegan a Doctor, que los necesita para detectar las CLI.

### 2. Plan vinculado (todo en Rust)
- Tras una vista previa `planned`, con `recoveryRequired: false` y cambios, `PlanStore` (un único slot; un contador de generación descarta las vistas previas que terminan después de una invalidación) guarda:
  - la huella **completa**;
  - las opciones;
  - el home analizado;
  - la lista `(kind, path)`.
- El webview solo recibe un id opaco de un solo uso: `plan-` seguido de 128 bits aleatorios del CSPRNG del sistema operativo (`getrandom`, ya presente en el árbol de dependencias), sin relación con la generación. Si el sistema no proporciona aleatoriedad, no se emite id. La comparación es en tiempo constante. La huella está en un campo `#[serde(skip)]`.
- Se invalida al iniciar otra vista previa, con `discard_plan` (la UI lo llama en cuanto cambian las opciones), al cumplirse 10 minutos, ante un id incorrecto y en **cualquier** intento de aplicación. Esto incluye el que choca con otra operación en curso: el plan se descarta y hay que generar una vista previa nueva.
- Una vista previa que termina después de un `discard` no puede guardar su plan.
- `apply_sync(token)` ejecuta `sync.py --apply --target … --format json [--specialists] [--upgrade-skills] --expect-plan <huella>`. El argv sigue siendo de literales, con una única excepción tipada: `Fingerprint`, que solo se construye a partir de la salida validada del núcleo. Las opciones salen del plan guardado, nunca de la UI. El núcleo reconstruye el plan bajo su bloqueo exclusivo y rechaza con `stale-plan` si algo cambió.

### 3. Clasificación del resultado (primero `transaction.outcome`, después `error.code`)

| Respuesta del núcleo | Resultado en Desktop |
| --- | --- |
| exit 0, `applied`, `committed`, `recoveryRequired: false`, `matched`, `expected` = huella guardada, mismo `home`, mismo lote `(kind, path)` | **Aplicado**; se confirma con una vista previa posterior que debe dar `unchanged` («verificado») |
| `lock-busy` (con precedencia; `not-started`) | Otra instalación en curso; no se sugiere `--recover` |
| `committed` + error | Aplicado con error posterior; **no reaplicar** (y limpiar si `cleanup-failed`) |
| `recovery-pending`, o `rolled-back`/`not-started` con `recoveryRequired: true` | Recuperación necesaria, con el comando del runtime integrado |
| `not-started` + `stale-plan` | Plan obsoleto; no se aplicó nada |
| `not-started`/`rolled-back` con `recoveryRequired: false` | Rechazo del núcleo; estado anterior intacto o restaurado |
| `unknown`, `recoveryRequired: null`, cualquier discrepancia o fallo tras lanzar el proceso | Estado desconocido; Diagnóstico se actualiza automáticamente |
| Fallo antes de lanzar (integridad, paquete, spawn, ocupado) | No se ejecutó nada |

Nunca se muestra éxito solo porque el proceso terminó.

### 4. Interfaz
- El botón «Aplicar N cambios…» solo aparece en un plan vigente. Si no está disponible, se explica el motivo: obsoleto, sin token, transacción en curso o recuperación pendiente según Diagnóstico.
- La confirmación usa un `<dialog>` modal nativo (sin permisos Tauri nuevos) con alcance, recuentos por cliente y advertencias. El foco inicial está en «Cancelar».
- Durante la aplicación no se pueden lanzar otras acciones, F5 no hace nada y la ventana no se puede cerrar.
- Después de cualquier intento, Diagnóstico se actualiza automáticamente.
- La recuperación se explica con pasos y el comando `& "<app>\python\python.exe" -I -B "<app>\syncode\scripts\sync.py" --recover`; la app **no** recupera.

### 5. Corrección en el núcleo
`write_with_backup` dejaba el temporal huérfano cuando el destino era de solo lectura en Windows: el modo copiado bloqueaba el `unlink` del `finally`. Ahora se restaura el permiso de escritura y se borra. El rollback era correcto; el defecto era el residuo. Test: `tests/test_sync_preview.py::FailedApplyRollbackTests`.

## Especialistas y resolución

`hub-application-security-auditor` no existe en esta instalación. La revisión de seguridad la hizo `hub-backend-auditor`, aplicando la skill `application-security-audit`.

| Recomendación | Origen | Decisión |
| --- | --- | --- |
| Clasificar por `outcome` antes que por código; `lock-busy` con precedencia; separar transporte antes/después de lanzar | Arquitectura | **Adoptada** |
| Incrustar el `BUNDLE_MANIFEST.json` en vez de hashear en `build.rs` | Arquitectura | **No adoptada**: la tabla se deriva de los bytes reales y también cubre el manifiesto; el coste es el mismo |
| No anclar handles (no cierra el TOCTOU frente al mismo usuario) | Arquitectura | **Adaptada**: se mantiene como capa barata (evita la sustitución entre la verificación y el uso), documentada como no defensa contra un atacante del mismo usuario |
| Sustituir la vista previa posterior por Doctor | Arquitectura | **Adaptada**: se hacen las dos (la vista previa da el «verificado»; Doctor refresca el estado global) |
| Contador de generación sin RNG; guard antes de consumir; no reutilizar la huella de un `stale-plan` | Arquitectura | **Adaptada**: la generación sigue descartando vistas previas obsoletas, pero el id es aleatorio (128 bits, CSPRNG del SO), como pidió seguridad, para que no sea predecible |
| `pyvenv.cfg`/`._pth` en la raíz; `cwd = python/`; sin `PATH` para sync; reenumerar tras anclar; `.pyc` plantados | Seguridad | **Adoptada** |
| Carrera vista previa/`discard`, TTL, id erróneo descarta el plan | Seguridad | **Adoptada** |
| Confirmación nativa desde Rust (MessageBoxW) | Seguridad | **No adoptada**: doble confirmación; con CSP estricta, sin contenido remoto y sin `innerHTML`, confirmar en la UI es un riesgo aceptado y documentado |
| Impedir el cierre de la ventana durante la aplicación; comparar `home` y lote | Seguridad | **Adoptada** |
| Huella en el argv del hijo | Seguridad | **Aceptada y documentada**: visible para procesos del mismo usuario, que ya pueden leer el home |
| Textos de transporte propios de la aplicación (nunca «Reintentar»); F5 bloqueado con el modal abierto; comando de recuperación del runtime integrado; un solo botón primario | UX | **Adoptada** |
| Botón «Copiar comando» | UX | **Adoptada** (`navigator.clipboard`, sin permisos Tauri) |
| Lista de copias `.bak` desde el resultado del núcleo | UX | **No adoptada**: `events[]` no es contrato; se informa de las copias sin listarlas |

## Consecuencias y riesgos

- **Mismo usuario**: NSIS (`currentUser`) y el ZIP se instalan en carpetas que el propio usuario puede modificar, y el exe no está firmado. La integridad protege contra un paquete corrupto, incompleto, mezclado o con archivos plantados, **no** contra un atacante con los privilegios del usuario, que puede sustituir el exe. Mitigación real: firma Authenticode e instalación por máquina.
- **Confirmación solo en la UI**: un webview comprometido podría pedir una vista previa y aplicarla. Se mitiga con la CSP y la ausencia de contenido remoto y de `innerHTML`.
- **Cierre**: si la app se cierra por la fuerza durante la aplicación, el proceso hijo termina la transacción pero el resultado no se muestra; Doctor lo reflejará.
- **Timeout**: la aplicación tiene 300 s. Matarla deja `recovery-pending`, que se presenta como estado desconocido con los pasos de recuperación.
- **Lote revisado frente a lote aplicado**: si el núcleo confirma la escritura pero el lote, la huella o el home no coinciden con lo revisado, el resultado es «desconocido» y nunca se presenta como éxito.
