# ADR-0004 — Registro de revisiones y aprobaciones de skills de terceros

**Estado:** Propuesto (Skill Scout v0.3, segundo incremento).

## Contexto

Skill Scout analiza datos no confiables de GitHub. El resultado de un escaneo estático no autoriza la copia de terceros, la instalación ni su posterior uso en Claude Code o Codex. Se necesita una separación verificable entre **candidato**, **revisión humana**, **aprobación versionada** y **promoción técnica**.

## Decisión

- Crear `scripts/skill_registry.py` sin escrituras, ejecución ni acceso a red.
- `review-template`: transformar un informe `inspect` de Skill Scout en una **ficha pendiente**, preservando enlace al commit, ruta, blob SHA, SHA-256 y señales detectadas. Dejar licencia, compatibilidad y aprobación en estados **no verificados**.
- `registry/approved-skills.json`: único manifiesto versionado para futuras incorporaciones; comienza **vacío**, sin aprobar ninguna skill. Estructura estricta `{schemaVersion:1, skills:[...]}`.
- Las entradas aprobadas deben declarar licencia verificada y evidencia HTTPS, aceptación explícita de los riesgos y su evidencia, compatibilidad revisada de ambos clientes (al menos uno probado), nombre y fecha del aprobador y enlace HTTPS a evidencia de aprobación. Rechazar duplicados, colisiones con las cuatro skills propias y fuentes que no coincidan con un SHA de commit completo.
- `validate` comprueba consistencia **estructural** del manifiesto, nunca autenticidad criptográfica de una aprobación humana.
- `plan` solo informa las rutas globales que se propondrían para una instalación futura y bloquea de manera conservadora los destinos existentes, enlaces simbólicos o padres no directorio. Todos los registros se etiquetan `PROPOSAL_ONLY`; no hay modo `--apply`.
- `scripts/sync.py` sigue sin leer `approved-skills.json`; no se implementa la instalación de terceros en este incremento.

## Consideraciones

La aprobación de metadatos versionados no verifica por sí sola la identidad del aprobador, la licencia real de una skill ni la integridad de su árbol de archivos. Antes de instalar habrá que volver a obtener el commit fijado, comprobar hashes y todos los artefactos necesarios, comprobar una licencia aplicable, considerar dependencias/MCP/permisos y realizar pruebas aisladas de compatibilidad. El futuro instalador deberá usar preflight global y respaldos para cada archivo, impedir sobreescrituras y requerir autorización explícita.

Incluso una ficha con estado `approved` es una declaración sujeta a revisión del PR del Hub, **no evidencia automática de confianza**. No pueden agregarse credenciales, clientes, datos internos ni código privativo al manifiesto público.

## Estado final de este incremento

Se entregan esquema/validaciones, plantilla y plan de solo lectura; el manifiesto permanece vacío. Ningún tercero se instala, no se cambian configuraciones globales y no hay automatización de fondo.
